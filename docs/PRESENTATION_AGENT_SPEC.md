# Presentation Agent Specification

Version: 1.0
Agent: `presentation` / 資料作成・発表AI

## 1. Purpose

Presentation Agent converts Agent 1 research evidence into decision-ready presentation artifacts. It is deliberately evidence-bounded: it improves structure and communication while preserving the truth state and source lineage established by Research Agent.

## 2. Design principles

### 2.1 Evidence before aesthetics

A polished slide must never be allowed to strengthen an uncertain statement. Verified facts, inferences, unresolved items and proposals remain separate classes throughout the pipeline.

### 2.2 LLM plans; deterministic code materializes facts

The local LLM is used for narrative planning: slide order, neutral titles, claim selection and proposal placement. It references evidence by stable claim IDs. Deterministic code then materializes exact Agent 1 claim text and source IDs into the deck.

This architecture reduces factual drift caused by free-form paraphrasing.

### 2.3 Presentation is a different artifact from research

Research may be detailed and source-heavy. A presentation must select only the evidence needed for the audience/purpose, make limitations visible and leave complete source URLs in appendices/metadata.

### 2.4 Fail closed on broken lineage

Unknown claim IDs, missing evidence, invalid research status or rendering failures do not produce a successful presentation status.

## 3. Pipeline

```text
Task + latest Agent 1 research JSON
              |
              v
        Evidence Gate
              |
              v
        Evidence Catalog
 F1/F2/... = verified facts
 I1/I2/... = inferences
              |
              v
          LLM Planner
  (select/order IDs only)
              |
              v
   Deterministic Validator
              |
              v
 Materialize exact evidence text
              |
       +------+------+
       |             |
     JSON/MD        PPTX
                       |
                  optional PDF
                       |
                       v
                 QA + lineage
```

## 4. Evidence gate

A normal live presentation requires research status `researched_with_sources` and at least one source-backed claim.

An explicit `--allow-incomplete-research` override exists for test/scaffold workflows. The override does not create factual evidence that is not present.

The exact input research file is fingerprinted with SHA-256 and stored in presentation metadata.

## 5. Evidence catalog

Agent 1 output is normalized to:

- `F1..Fn` — verified facts
- `I1..In` — inferences

Each catalog item retains:

- exact claim text
- class (`verified_fact` or `inference`)
- Agent 1 source IDs (`S1`, `S2`, ...)

The catalog also carries unresolved items, conclusion and recommended next actions.

## 6. Planner contract

The model returns JSON only. It may choose:

- presentation title/subtitle
- slide order
- slide kind
- unique neutral slide titles
- evidence claim IDs to show
- explicit proposals/recommendations
- non-factual context
- delivery-oriented speaker notes

The model must not provide rewritten factual body text. Visible factual body text is later copied from the evidence catalog.

## 7. Validation rules

The deterministic validator requires:

- non-empty slide array
- unique slide titles
- only known claim IDs
- maximum four evidence claims per ordinary slide
- maximum six visible items per ordinary slide
- valid output language (`ja`, `en`, `vi`)
- requested slide budget between 3 and 20

Unknown claim IDs cause hard failure rather than silent removal.

## 8. Source and limitation appendices

Source slides are generated by code, not by the LLM. They contain only sources actually used by selected claims.

If Agent 1 recorded unresolved items, a limitation appendix is generated automatically. These items are copied from Agent 1 rather than rewritten as new conclusions.

## 9. PPTX renderer

Renderer baseline:

- 16:9 widescreen
- unique visible title on each slide
- title font ~30–36 pt
- body font target 20 pt
- deterministic object insertion order
- source IDs in footer
- speaker notes include evidence source IDs
- source/limitation slides use the same readable layout
- no image-only communication in V1

The implementation uses `python-pptx` and therefore does not require Microsoft PowerPoint on the Ubuntu AI server.

## 10. PDF

`--format pdf` and `--format all` first generate PPTX and then invoke LibreOffice/`soffice` in headless mode. If LibreOffice is not installed, the request fails explicitly. PDF is therefore an optional host capability, not silently emulated.

## 11. QA metadata

`presentation-qa/v1` records:

- pass/fail state
- validation warnings/errors
- unique-title status
- evidence-bounded visible-fact status
- referenced vs available claim count
- evidence coverage ratio
- source appendix presence
- structural accessibility targets

This is structural QA, not pixel-level visual inspection. Pixel/render QA can be added later through LibreOffice rendering plus image inspection.

## 12. CLI

Typical Japanese internal presentation:

```bash
3agent presentation TASK-YYYYMMDD-0001 \
  --live \
  --audience "部長・R&Dチーム" \
  --purpose "技術選定の判断" \
  --language ja \
  --slides 6 \
  --format pptx
```

Source-only generation:

```bash
3agent presentation TASK-YYYYMMDD-0001 --live --format source
```

PDF when LibreOffice is present:

```bash
3agent presentation TASK-YYYYMMDD-0001 --live --format pdf
```

## 13. Artifact contract

`presentation-artifact/v1` contains:

- `task_id`
- `agent_id`
- `status`
- `source_research_artifact`
- `source_research_sha256`
- `source_research_status`
- presentation options
- validated plan
- QA
- generated artifact paths
- timestamp

## 14. Acceptance criteria

Agent 2 V1 is accepted when automated tests prove:

1. evidence catalog preserves facts/inferences/source IDs
2. unknown claim references are rejected
3. duplicate titles are rejected
4. source and limitation appendices are deterministic
5. research artifacts can be found across date directories
6. PPTX opens successfully through `python-pptx`
7. PPTX slide titles match validated plan
8. speaker notes are writable/readable
9. dry-run remains explicitly non-factual
10. legacy harness dry-run contract still passes

## 15. Future extensions

- company PPTX template/theme ingestion
- charts generated from structured numeric evidence
- image/diagram planning with alt-text contract
- pixel-level visual QA from rendered slide images
- slide revision loop based on QA score
- multi-model routing for presentation planning vs visual/layout review
- Japanese corporate writing style profiles by audience level
