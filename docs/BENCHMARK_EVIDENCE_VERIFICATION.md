# Fixed Benchmark Evidence Verification v1

The dual-RTX5090 context-packing benchmark now has a second deterministic trust boundary after execution.

The benchmark runner produces evidence. `workspace-benchmark-verify` independently reloads that evidence and recomputes the trust-critical claims before publication.

Schema:

`workspace-benchmark-evidence-verification/v1`

## Commands

After the fixed suite finishes, publishable paths are canonicalized:

```bash
workspace-benchmark-canonicalize --root /path/to/benchmark-root
```

Then the evidence set is independently verified:

```bash
workspace-benchmark-verify \
  --source-ref <exact-40-hex-sha> \
  --root /path/to/benchmark-root \
  --repo-root /path/to/exact-checkout \
  --task-set /path/to/exact-checkout/benchmarks/fixed_task_set_v1.json \
  --output /path/to/benchmark-root/verification.json
```

## Why a second verifier exists

`suite.json` is generated by the benchmark runner itself. Treating its own `promotion_eligible` flag as independent evidence would create a self-assertion boundary.

The verifier therefore does not simply trust the suite summary. It reopens the underlying manifests and receipts and recomputes the important decisions.

## Verification contract

A PASS requires all of the following:

1. `environment.json` validates as `workspace-benchmark-readiness/v1`, is `ready=true`, and is bound to the exact requested source SHA;
2. the versioned task-set ID, canonical SHA-256, case IDs and count match the repository task set;
3. fixture content is reread from the exact checkout and the fixture-corpus SHA-256 is independently recomputed;
4. exactly the four expected variants exist:
   - `baseline-legacy-48k`
   - `ranked-48k`
   - `ranked-40k`
   - `ranked-32k`;
5. every `benchmark.json` validates its internal metrics hash, task-scope hash, exact source ref, configuration fingerprint and current metric-registry fingerprint;
6. all variants use the identical runtime task IDs and exact fixed case order;
7. every `isolation.json` proves isolated DB/artifact/telemetry/audit sinks and no raw prompt/evidence logging;
8. validator acceptance is recomputed from the per-case validator receipts;
9. `OptimizationAcceptanceGate` is rerun from the baseline/candidate benchmark manifests;
10. the recomputed comparison must exactly equal the comparison recorded in `suite.json`.

A change to the suite summary alone therefore cannot manufacture promotion eligibility.

## Artifact canonicalization and path privacy

The benchmark runner historically writes local absolute `manifest_path` values into `suite.json`. On a self-hosted runner, an absolute path can expose local runner filesystem naming even though it is not business data.

Before publication, `workspace-benchmark-canonicalize` verifies each recorded path resolves to the expected `<benchmark-root>/<variant>/benchmark.json` and rewrites **only** that field to `<variant>/benchmark.json`.

The workflow also suppresses the raw `workspace-benchmark` stdout so the pre-canonicalized absolute paths are not copied into Actions logs.

The canonicalizer fails closed if a path points anywhere else. Metrics, hashes, cases, comparisons and security fields are never modified.

## Verification receipt

A successful `verification.json` records only metadata:

- exact source SHA;
- task-set ID/SHA/count;
- independently recomputed fixture-corpus SHA;
- current metric-registry SHA;
- environment and readiness receipt fingerprints;
- boolean verification checks;
- candidate `promotion_eligible` verdicts as independently recomputed;
- SHA-256 for each published source evidence file;
- canonical verification receipt SHA-256.

It does not copy raw prompts, raw evidence, model output, credentials or business content.

## Scope limit

This verifier validates the fixed context-packing benchmark evidence contract only. It does not convert a single-source packing comparison into D7-06 concurrency/cache evidence, does not self-issue evaluator attestation, and does not satisfy D7-05 external holdout requirements.

Real hardware execution is still mandatory. An unexecuted workflow remains unverified regardless of implementation readiness.
